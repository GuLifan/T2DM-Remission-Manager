## 一、审阅方式（先说清楚结论是怎么来的）

| 项目 | 说明 |
| --- | --- |
| 审阅身份 | 以"**几乎不懂代码的门诊医生**"视角操作，只看界面本身能不能让人放心、快速、不出错地完成临床工作 |
| 操作环境 | 真实浏览器（Chrome），后端 127.0.0.1:8088，真实数据流（不是看代码推测） |
| 实际走通的页面 | 患者列表与建档、患者工作台（常规管理）、60秒预评估、完整评估、阶段复评、缓解观察期（到期）、缓解判定（核对+结果+医生确认面板） |
| 未走到的页面 | 缓解后复评、关闭路径、急性安全快速建档（**这些页面的问题在本文件中标注为"未实测"**，供你判断是否要先看） |
| 对照标准 | Jakob Nielsen《十大可用性启发式》；GOV.UK 设计系统（表单模式，含"一次只问一件事"）；NHS 设计系统（英国 NHS 服务手册） |
| 截图证据 | 本文件同目录 `审阅截图/review_01…07.png` |

### 我这次审阅暴露出的根本问题（自我反省，写在最前面）

我把界面当成"**把后端已有的字段都摆出来**"来做，而不是按"**医生在门诊那 3 分钟里要做的动作**"来设计。结果就是：

- 工程概念直接搬到了界面上（"未生效的分支""客观条件""实际可执行性"）；
- 一屏里塞进所有可能用到的输入项，哪怕 90% 的情况只用得上其中两三个；
- 系统状态和病人状态混在一起展示，甚至出现与事实不符的标签（见 UX-01）。

这三点是下面绝大多数问题的**同一个根因**。

## 二、问题清单

> **严重度约定**：
> **P1 = 会误导临床判断、或可能造成误操作/数据丢失**；
> **P2 = 明显影响效率或需要反复确认**；
> **P3 = 影响观感或细节体验**。
> 每条都留了「**你的修改**」栏，你直接写你的判断和要求即可（也可以整条划掉）。

### A. 会误导医生的问题（最优先）

| 编号 | 位置 | 我看到的（医生视角） | 为什么成问题 | 建议方向 | 严重度 | 你的修改 |
| --- | --- | --- | --- | --- | --- | --- |
| UX-01 | 患者工作台 顶部徽章（观察期页、判定页） | 患者明明在**缓解观察期**、在**缓解判定**，右上角徽章却写着"**常规糖尿病综合管理**" | **显示的信息与事实相反**。医生可能据此判断"这个患者已经回到常规管理了" | 徽章应显示**当前环节的中文名**（如"缓解观察期""缓解判定"）；没有阶段概念的环节不要回退成"常规管理" | P1 |  |
| UX-02 | 患者列表 "当前环节"列 | 内容显示"缓解诱导"（这是**阶段**），而列名是"**环节**" | 列名与内容不是一回事：环节应是"阶段复评"，阶段才是"缓解诱导"。医生会理解错 | 要么列名改"当前阶段"，要么列内容改显示环节（并另列阶段） | P1 |  |
| UX-03 | 阶段复评 分支区 | 先选"常规复评动作（继续／调整／转换阶段／结束主动管理）"，**然后在下面还要再选一次**"本次复评动作" | 同一个决定问了两次，医生会怀疑自己上一次选错了；也容易只改一处导致不一致 | 取消"常规复评动作"这一项，直接把 4 个动作作为并列选项；分支与动作合成一次选择 | P1 |  |
| UX-04 | 缓解观察期 "重新用药"区 | 两个下拉框**已经预填了默认值**（因高血糖 / 血糖稳定），旁边就是"记录重新用药并返回阶段复评"按钮 | **误点一次就写入一条错误的用药记录并改变患者状态**；而这条记录会永久留在事件流水里 | 该区默认折叠；展开后下拉框应留空并要求医生主动选择；执行前必须二次确认 | P1 |  |
| UX-05 | 阶段复评 "新发生的安全问题／核心治疗变化" | "**无**"也是一个可勾选项，且**默认已勾**；勾"低血糖"时若忘记取消"无"，记录里会同时存在"无"和"低血糖" | 产生**自相矛盾的临床记录**；且系统不拦 | "无"改为独立开关；或勾选其他项时自动取消"无"并禁用；后端也应校验 | P1 |  |
| UX-06 | 缓解判定页 | 点"核对客观条件"后，**结果文字出现在视口上方之外**（需要向上滚动才看得到），很容易以为没反应 | 关键结论看不见 → 医生反复点击或直接放弃 | 核对后应把结论**置顶或弹到眼前**，并在操作条上同步显示结论摘要 | P1 |  |
| UX-07 | 缓解判定页 "返回主动管理后的管理阶段" | 无条件显示，默认"暂不返回阶段"，但医生不知道**什么时候需要填** | 不确定要不要填 → 要么乱填，要么卡住 | 只在"仍用药/未达标"这类情形出现时再显示；或明确写成条件句 | P2 |  |
| UX-08 | 全站 术语 | "未生效的分支""客观条件""实际可执行性""一个主要阶段指标" | 都是**工程/系统语言**，不是门诊用语；Nielsen #2「系统语言应与真实世界一致」 | 换成医生嘴里的话：如"本次复诊属于哪种情况""是否符合缓解标准" | P1 |  |
| UX-09 | 全站 提示文字 | 提示多为**整句、带句号、有时两三句**（如"日常滴定、上传血糖和一般随访不生成正式复评节点。"） | GOV.UK 表单规范：提示应**单句、尽量简短、不加句号**；长解释会拖慢扫读 | 每条提示压到一行以内；需要长解释的改为页面说明段落 | P2 |  |

### B. 信息架构与"一屏该放多少"

| 编号 | 位置 | 我看到的 | 为什么成问题 | 建议方向 | 严重度 | 你的修改 |
| --- | --- | --- | --- | --- | --- | --- |
| UX-10 | 阶段复评页 | 一屏塞了 **4 组多选 + 4 个分支单选 + 分支专属字段 + 复评日期**，实测要滚**三屏以上**；而这次决定实际只用得上 3–5 项 | GOV.UK 核心原则「**一次只问一件事**」；Nielsen #8「极简设计」 | 按分支**分步**：先选"本次属于哪种情况"，再只显示该类情况的 1–2 个必填项；其余收进"更多选项" | P1 |  |
| UX-11 | 阶段复评页 | 页面很长，医生滚到底部按下按钮后，**看不到自己上面填了什么** | 临床记录需要"提交前核对"（GOV.UK 有 Check your answers 模式） | 提交前给一个"本次记录摘要"确认块 | P2 |  |
| UX-12 | 患者工作台 页头 | 页头标题写"**患者管理**"（这是列表页的名字），下面内容区标题又写"阶段复评与治疗调整" | 两个标题打架，医生说不出"我现在在哪个页面" | 页头应显示**当前环节名**；患者信息作为副行 | P2 |  |
| UX-13 | 每个页面底部「本次管理记录」 | 需要滚很久才看到；但它是"这个患者之前发生了什么"的核心 | 关键上下文被埋 | 提到侧栏或页头右侧做"病史时间线"，或做成可展开抽屉 | P2 |  |
| UX-14 | 患者工作台 | 没有"这个患者的关键信息摘要"（诊断、当前用药、HbA1c 变化） | 每次都要靠翻事件流水回忆 | 页头下方加一行关键信息（一行内） | P2 |  |

### C. 操作、反馈与数据安全

| 编号 | 位置 | 我看到的 | 为什么成问题 | 建议方向 | 严重度 | 你的修改 |
| --- | --- | --- | --- | --- | --- | --- |
| UX-15 | 全站 不可逆操作 | 「结束主动管理」「关闭本路径」「确认2型糖尿病缓解」点击后**直接执行**，没有任何二次确认 | 组件库里已经做好了确认对话框（`ConfirmDialog`），但**一个都没用上**；Nielsen #5「错误预防」 | 不可逆动作一律二次确认，确认框里写清后果 | P1 |  |
| UX-16 | 阶段复评等长表单 | 填到一半点左侧"完整评估与计划"（可回看的项），**表单内容直接丢失且无任何提示** | 白填一次；门诊场景下医生会非常恼火；Nielsen #3「用户控制与自由」 | 有未提交内容时离开前提示；或自动暂存草稿 | P1 |  |
| UX-17 | 提交后 | 整个页面（含侧栏、页头）闪成一句"正在读取患者信息…" | 看起来像掉线/崩溃 | 保持框架不变，只在内容区显示加载态 | P2 |  |
| UX-18 | 提交后 | 状态跳转与按钮变化同时发生，没有"已记录，下一步是…"的收尾 | 医生不确定是否成功 | 提交后给明确的完成提示 + 下一步指引 | P2 |  |
| UX-19 | 页头 + 侧栏 | "查阅医学依据"和侧栏"医学依据"是**同一个抽屉的两个入口** | 重复入口造成"是不是两个不同功能"的疑问 | 只留一个 | P3 |  |
| UX-20 | 缓解判定页 | 流程其实是"核对 → 记录 → 医生确认"三步，但界面**没有步骤感**，按钮是"点了才长出来"的 | 医生不知道总共要走几步、现在第几步 | 显示步骤提示，或把三步合并成一次"核对并记录" | P2 |  |

## 四、修订方式（给 Lifan 用）

1. 你直接在每条问题的「**你的修改**」栏写意见：可以写"同意/不同意/改成 …"，也可以写你自己使用时的感受。
2. 你可以在文件末尾追加**新条目**（沿用 UX-编号，从 UX-37 起），或整段删掉你不同意的问题。
3. 你也可以调整**严重度**（P1/P2/P3）——这是给我排优先级的。
4. 你改完告诉我，我会：
   - 先按你的修改同步 `UI.md` 与 `_SPEC` 相关文档（涉及规范的部分）；
   - 再改代码，**逐条回填"处理结论 + 提交号"**；
   - 完成后把本文件状态从"待 Lifan 修订"改为"v1.1 已实施"。
