## 一、目标与边界

M7 的目标不是简单运行一次 `scripts/build.py`，而是把当前开发态系统收敛为一套可核验、可移交、无真实患者数据的 Windows 交付物，并保证软件、实现表、状态图、病例走查和交付说明相互一致。

本阶段包括：

1. 加固 Windows `onedir` 便携版构建与启动/退出流程。
2. 在隔离数据目录完成自动化 E2E 和 3 个锁定病例走查。
3. 生成临床流程实现表、状态转换图、病例走查与问题清单及交付说明。
4. 验证正式包不含真实患者数据、测试能力、账号、密钥、日志或未经授权的医学原文。
5. 在无项目虚拟环境依赖的 Windows 环境完成双击运行验收。

本阶段不包括：

1. 不修改锁定临床节点、阈值、分支、字段或自然语言输出。
2. 不新增患者临床数据导出功能；如需此功能，应另立需求与隐私方案。
3. 不把开发库 `data/runtime/etmms.db`、`secret.key`、日志或任何测试数据带入交付包。
4. 不在缺少明确许可时，把受版权保护的完整 PDF 或其预构建全文索引随软件分发。
5. 不在未完成医学复核时，把 M6-D 的 36 条候选写成“已确认医学依据”。
6. 不自动合并或推送 `main`；分支动作继续由 Lifan 单独授权。

## 二、已核实的当前事实

### 2.1 构建与启动现状

| 核对项 | 当前事实 | M7 影响 |
| --- | --- | --- |
| Python / PyInstaller | 项目内 Python 3.14.4；`uv.lock` 锁定 PyInstaller 6.22.3；M1 兼容性烟测通过 | 可继续使用 `onedir`，但必须复测完整应用 |
| 构建脚本 | `scripts/build.py` 只构建前端、复制静态文件并调用 PyInstaller | 尚未形成可交付流水线 |
| Alembic 资源 | 运行时依赖 `backend/alembic.ini` 与 `backend/migrations/` | 现脚本没有显式打入，首次建库存在失败风险 |
| 静态资源 | `backend/app/static` 当前不存在，由构建脚本临时生成 | 构建必须先完成前端并验证入口/资产完整性 |
| 启动就绪 | `run_app.py` 固定等待 2 秒后打开浏览器 | 慢机可能先打开错误页；应改为健康检查就绪后打开 |
| 退出方式 | 当前只有阻塞式 Uvicorn 进程，无托盘菜单 | 与 `_SPEC/07` 已批准的“托盘退出”路线不一致 |
| 日志 | 当前仅输出到标准输出，没有正式文件日志 | 无控制台的正式启动器将缺少可诊断证据 |
| 数据目录 | 冻结运行写 `%LOCALAPPDATA%\ETMMS` | 方向正确；需补首次运行、备份和卸载说明 |
| 测试模式 | 默认 `false`，但仍可被环境变量覆盖 | 正式冻结包需强制关闭，不能只依赖默认值 |
| 产物 | `release/` 当前没有正式产物 | M7 不继承任何旧二进制基线 |

PyInstaller 6.22.3 官方说明确认：`onedir` 运行时包内资源位于 `_internal`，数据文件需要显式加入并保持代码期望的相对位置。因此 M7 应保存稳定的 `.spec` 文件，而不是只依赖临时命令行参数。

## 三、待审批的约束决议

### M7-D01｜医学依据如何进入交付环境

**建议结论：选择 A。**

- **A（建议）｜本地授权材料导入**：基础便携包不含三份 PDF、PDF 全文或预建全文索引。首次管理员可在本机选择三份已获授权的 PDF，后端校验文件名、SHA-256 与页数后导入 `%LOCALAPPDATA%\ETMMS`；临时上传文件立即删除，只保留本机检索索引。锁定稿作为项目资源随包导入。
- B｜授权材料随包：仅在 Lifan 提供明确的分发范围与授权依据后，将获授权材料作为独立资料包携带；必须附来源、许可和适用范围说明。
- C｜仅内置 2026 CC BY 材料：法律边界最清楚，但会导致四来源完整性门禁长期失败，**不建议**。

采用 A 后，软件仍能达到“四来源可检索”，但检索库由接收方在本机从其合法持有的材料生成，而不是由 ETMMS 发布包传播全文。

### M7-D02｜正式包测试能力边界

**建议结论：正式冻结包强制 `test_mode=false`，忽略外部 `ETMMS_TEST_MODE=true`；测试能力只存在于开发/验收运行。**

1. 正式包不含 `.env`、测试账号、测试患者或 `source='debug'` 事件。
2. 首次运行创建的第一个账号仍是正式管理员，但 `is_test_account=false`。
3. 正式包启动后，模拟日期与调试跳转接口必须返回 403。
4. 3 病例 E2E 使用独立验收数据目录和测试模式，完成后整目录删除，不从验收库复制正式包数据库。

### M7-D03｜构建定义与资源范围

**建议结论：新增受版本控制的 `packaging/ETMMS.spec`，`scripts/build.py` 只负责编排与门禁。**

必须打入：

- 前端静态构建产物；
- `alembic.ini`、迁移环境和全部迁移版本；
- 项目自有的临床流程锁定稿资源；
- 应用图标、版本信息、第三方许可与基础交付说明。

禁止打入：

- `data/runtime`、任何 `.db`、`secret.key`、`.env`、日志；
- `_DEV/医学依据` 与甲方原件；
- 测试、缓存、源码映射、Node 开发依赖和临时截图；
- 用户目录中的任何既有 ETMMS 数据。

构建前后均做清单扫描；命中禁止项立即停止，不允许人工删除后继续伪装通过。

### M7-D04｜启动、诊断与退出体验

**建议结论：兑现 `_SPEC/07` 已批准的托盘启动器路线。**

1. 单实例运行；重复双击时打开现有页面，不再启动第二个服务。
2. 服务健康检查成功后再打开浏览器，不使用固定 2 秒猜测。
3. 8088 被其他进程占用时给出中文可操作错误，不打开未知服务页面。
4. 托盘菜单至少包含“打开 ETMMS”“打开数据目录”“退出 ETMMS”。
5. “退出”必须停止 Uvicorn 并释放端口；不得依赖用户结束任务。
6. 日志写 `%LOCALAPPDATA%\ETMMS\logs`，采用滚动文件；日志不得记录患者完整病历、密码、会话令牌或检索正文。
7. 如引入 `pystray`/`Pillow`，只加入项目依赖并锁定版本，不改全局环境。

### M7-D05｜浏览器自动化与 3 病例验收

**建议结论：补齐 Playwright，作为 M7 正式 Gate，不再只依赖人工走查。**

1. Playwright 及浏览器内核仅为开发依赖，不进入交付包。
2. 在隔离数据目录完成登录、建档、6 个流程单元、日期推进、权限/只读、依据抽屉及 3 个锁定病例。
3. 每个病例同时记录预期输出、实际输出、状态变化、规则 ID、截图证据和是否一致。
4. 自动化 Gate 之后再执行一次真实浏览器人工走查，覆盖托盘、双击启动、焦点、下载/文件选择等自动化难以可靠验证的系统行为。

### M7-D06｜“干净环境”验收口径

**建议结论：采用两级 Gate。**

- **Gate 1｜本机隔离烟测**：从 `release/` 复制到临时目录，清理 Python/Node/uv/npm 等开发路径，只通过 `ETMMS.exe` 启动；验证迁移、登录、静态资源、SQLite/FTS5、退出和重启持久化。
- **Gate 2｜外部干净 Windows**：在另一台未安装 Python/Node 的 Windows x64，或经 Lifan 单独批准后启用的 Windows Sandbox/虚拟机中双击验收。

本机当前没有 Windows Sandbox，因此 Gate 2 是最终交付的外部依赖。未完成 Gate 2 时可以完成候选包，但不得宣称“干净环境验收通过”。

### M7-D07｜交付文档格式与来源

**建议结论：建立 `_DELIVERY/v1.0.0/` 作为无患者数据、可版本控制的交付文档目录。**

1. **临床流程实现表**：以甲方 v0.1 原表的 5 个工作表和视觉结构为基线；保留原 5 个工作表名称与顺序，增加 `实现追溯` 工作表。追溯内容来自 `MAPPING.md`、代码测试和 M6-D 复核状态，不手工复制另一份规则真源。
2. **状态转换图**：交付 Mermaid 源文件 `.md`、可浏览的 `.svg` 和便于打印的 `.pdf`；图由状态/转换定义生成并与代码边集合自动比对。除非 Lifan 另有要求，不增加 draw.io 作为第二套手工真源。
3. **病例走查与问题清单**：交付 `.xlsx` + `.md`。Excel 至少含 `说明`、`病例1`、`病例2`、`病例3`、`问题清单` 5 个工作表；只用任务书中的合成病例，不含真实患者数据。
4. **交付说明**：记录版本、运行与退出、数据目录、备份/卸载、依据导入、权限边界、已完成、未完成、已知问题和支持范围。
5. **清单与许可**：生成 `SHA256SUMS.txt`、文件清单、第三方软件许可清单；如分发 CC BY 材料，另附完整署名和许可链接。

正式可传输包命名建议：`ETMMS-v1.0.0-win-x64.zip`。禁止使用“最终版”“最新版”等模糊名称。

### M7-D08｜“导出审计”的范围

**建议结论：M7 不新增患者数据导出。**

1. `_SPEC/08` M2 中“导出审计在 M7 接入”按历史未落地设想处理，在本方案获批后改为“不适用：V1.0 没有患者数据导出需求”。
2. 领域定义只读接口不是患者数据导出，不额外写审计。
3. 离线生成实现表、状态图和病例走查属于构建过程，不写运行库审计。
4. 若将来需要患者数据导出，必须另行定义字段最小化、权限、脱敏、文件保护、审计内容和撤销/清理策略。

### M7-D09｜签名与发布架构

**建议结论：本轮发布 Windows x64 无签名候选包，并在交付说明中明确 SmartScreen 可能提示；如 Lifan 提供代码签名证书，再增加签名 Gate。**

当前没有签名证书或组织发布流程，不能把“未签名”伪装成已验证发布者。M7 不自动申请证书，也不把证书私钥存入仓库。

### M7-D10｜36 条依据候选与正式交付边界

**建议结论：工程打包可以先行，但面向临床使用的正式交付必须满足以下二选一。**

- A｜36/36 条由 Lifan/医学负责人逐行复核并记录结论；或
- B｜交付说明、实现表和软件用途声明均明确“依据映射仍为候选，仅限内部技术验收，不构成医学确认”，且交付范围限制为内部评估。

未经 A 或 B 明确确认，不得把候选状态静默改成已确认，也不得对外宣称医学依据审定完成。

## 五、实施批次

### M7-A｜发布基线与版权安全入口

1. 按获批决议修订 `_SPEC/06–08` 的分发、测试模式与导出审计口径。
2. 新增稳定 PyInstaller spec，补齐静态资源、Alembic 和版本资源。
3. 加固冻结包配置：测试模式强制关闭、数据目录固定、资源定位统一。
4. 实现本地授权材料导入入口及哈希/页数门禁；不持久保留上传 PDF。
5. 实现正式文件日志、健康就绪、端口冲突和单实例基础能力。

**M7-A Gate**：首次运行可自动迁移；空数据启动成功；正式包测试接口 403；禁止项扫描为 0；三份本地授权材料可导入为 4/4 完整库；删除临时源文件后检索仍可用。

### M7-B｜启动器、自动化与候选包

1. 完成托盘菜单、优雅退出、重复启动和重启持久化。
2. 补 Playwright 浏览器自动化和 3 病例脚本。
3. 在隔离验收库完成权限、只读、依据检索、焦点和错误恢复验证。
4. 生成首个候选便携包并执行本机隔离烟测。

**M7-B Gate**：后端/前端/文档 Gate 全绿；Playwright 全绿；3 病例无错误排除、错误缓解确认或错误停药提示；退出后端口释放；候选包不调用系统 Python/Node。

### M7-C｜正式交付文档

1. 生成临床流程实现表 xlsx + md，并与代码/测试/依据状态做机器核对。
2. 生成状态转换图 md + svg + pdf，并比对全部状态与转换边。
3. 基于 Playwright/真实浏览器结果生成病例走查 xlsx + md 和合并问题清单。
4. 生成交付说明、第三方许可清单和文件校验清单。
5. 对 Excel/PDF/SVG 做逐页、逐表视觉检查。

**M7-C Gate**：原 5 个实现表工作表保留且内容与当前实现一致；追溯表无缺失规则；状态图无缺边/多边；病例表字段完整；无真实患者信息；所有视觉产物清晰可读。

### M7-D｜最终清洁构建与外部验收

1. 从已通过 Gate 的提交执行一次全新构建，不复用旧 `release/` 或旧 PyInstaller 工作目录。
2. 扫描包内容、依赖、版本、禁止项和 SHA-256。
3. 执行本机隔离 Gate 和外部干净 Windows Gate。

## 六、交付物详细验收口径

### 6.1 便携版

- Windows x64、`onedir`、绑定 `127.0.0.1:8088`。
- 不要求安装 Python、Node、uv 或 npm。
- 第一次双击自动创建用户数据目录、密钥和空数据库，并迁移到当前 head。
- 浏览器只在健康检查通过后打开；重复双击复用现有实例。
- 退出后 8088 监听消失，数据库完整性与外键检查通过。
- 复制到含中文或空格的路径仍可运行。
- 软件目录只读时仍能正常写用户数据目录。

### 6.2 临床流程实现表

- 继承甲方原表的 5 个工作表、表头体系、交替行色和冻结窗格。
- 状态、规则、字段、输出模板数量与 `_SPEC`/代码一致。
- `实现追溯` 至少包含：规则 ID、代码位置、测试位置、映射状态、依据复核状态、差异说明。
- M6-D 未经复核的内容必须显示“待 Lifan/医学负责人复核”。
- 不在表中嵌入患者数据或整段医学原文。

### 6.3 状态转换图

- 区分医生决策事件、管理状态、系统自动状态和关闭路径。
- 显示所有暂缓返回、观察期退出、判定失败/不确定和缓解终止返回。
- 不把标签或提醒画成新的临床节点。
- 图形边集合与 `domain/transitions.py` 自动核对。

### 6.4 病例走查与问题清单

每一步至少记录：

- 病例编号、步骤、页面/事件；
- 输入与前置状态；
- 预期输出、实际输出；
- 预期/实际目标状态；
- 规则 ID、截图/测试证据；
- 是否一致、严重程度、建议处理；
- 是否需要医生确认、处理状态。

问题清单必须合并去重，不把纯技术修复误写成待临床决定。

### 6.5 交付说明

必须说明：

1. 软件用途与“医生负责医学决定”的边界；
2. 安装、首次运行、打开、退出、备份、迁移和卸载；
3. 数据目录、单机/单 worker、账号定位和日志范围；
4. 医学材料由接收方本地导入及版权责任边界；
5. 已完成、未完成、已知问题、未经验证的环境；
6. 版本、提交号、构建时间、目标架构和 SHA-256；
7. 医学复核状态与适用的交付范围。

## 八、停止条件

出现以下任一情况立即停止对应批次并报告，不自行绕过：

1. 三份 PDF 的分发选择未获 Lifan 明确批准。
2. 构建包命中数据库、密钥、日志、真实患者数据、测试数据或未经授权原文。
3. 冻结包无法执行 Alembic 迁移，或使用 `create_all` 绕过迁移。
4. 正式包测试模式可被开启，或调试接口未返回 403。
5. 3 病例出现错误排除、错误缓解确认、错误停药提示或无出口状态。
6. 生成的实现表/状态图与锁定稿、代码或测试不一致。
7. 依据索引导入出现哈希/页数异常、半导入或错误材料覆盖。
8. 干净环境不可获得却准备宣称该 Gate 已通过。
9. 医学候选未复核且交付物没有明确限制为内部技术验收。
10. 需要代码签名但没有证书/私钥管理授权。
