# 07 技术架构与数据模型

> 早期2型糖尿病缓解管理软件（ETMMS）｜Spec 文档 07/08
> **版本**：v1.0｜**日期**：2026-09-19｜**状态**：有效（V1.0 基线）
> 本文件定义 V1.0 的工程架构、数据模型与关键实现约定。**临床规则不在本文件中定义**——临床规则见 01–05，UI 见根目录 `UI.md`。

---

## 一、架构总览

```txt
┌────────────────────────────────────────────────────────────┐
│  React + TypeScript 前端（SPA，Chrome 呈现）                 │
│  组件库 → 页面组装 → 分支按优先级渲染                          │
├────────────────────────────────────────────────────────────┤
│  FastAPI 接口层（api）                                       │
│  参数校验、鉴权、错误转换；不含临床判断逻辑                     │
├────────────────────────────────────────────────────────────┤
│  临床服务层（services）★最严格                                │
│  纯函数：输入 + 患者上下文 + today → 结论                      │
├────────────────────────────────────────────────────────────┤
│  领域层（domain）                                            │
│  状态转换表、分支优先级表、输出模板、枚举常量（单一数据源）       │
├────────────────────────────────────────────────────────────┤
│  数据访问层（repository）                                    │
│  ORM 查询封装；事务边界；事件与审计写入                         │
├────────────────────────────────────────────────────────────┤
│  SQLite（WAL）+ Alembic 迁移                                 │
└────────────────────────────────────────────────────────────┘
```

**分层铁律**

1. 接口层不写临床判断；服务层不直接访问 HTTP 上下文。
2. 领域层是**唯一数据源**（状态、分支优先级、模板、枚举），前后端与文档三处必须一致。
3. 所有状态跳转必须先经 `validate_transition()`；非法跳转一律拒绝并返回自然语言原因。
4. 服务层函数为**纯函数**：不读系统时间、不写数据库；时间由 `today` 参数注入，持久化由接口层完成。

## 三、领域层：单一数据源

### 3.1 状态与转换表

- `domain/states.py`：9 个状态常量与中文名称（前台只显示中文）。
- `domain/transitions.py`：合法转换表，每条形如

```python
Transition(
    rule_id="E3-B07",
    source=(ST31, ST32),
    target=ST40,
    required_fields=("f035_stop_last_med", "f036_stop_date"),
    side_effects=("record_med_stop_date", "enter_observation", "compute_earliest_judge_date"),
    template_id="OUT-E3-OBS-ENTER",
    guard=None,
)
```

- 新增或修改分支 = 改这张表 + 改 `_SPEC` + 改测试，三者必须同时提交。

### 3.2 分支优先级表（V1.0 关键改进）

V0.1 的缺陷：阶段复评的 8 个分支在界面上是 4 组独立勾选框，优先级隐含在服务层代码里，医生同时勾选时高优先级分支会静默覆盖低优先级分支。

V1.0 的做法：把优先级显式写进领域层，并**同时导出给前端**。

```python
# 阶段复评分支优先级（数字小者优先）
PHASE_REVIEW_PRIORITY = (
    Branch(priority=1, rule_id="E3-B08", key="uncontrolled",
           label="存在明显血糖失控", template_id="OUT-E3-ADJUST", target=ST31),
    Branch(priority=2, rule_id="E3-B06", key="on_treatment_non_diabetic",
           label="治疗下血糖已达非糖尿病范围且仍用获益药", template_id="OUT-E3-ON-TREATMENT", target="current"),
    Branch(priority=3, rule_id="E3-B07", key="stop_last_med",
           label="停用最后一种具有降糖作用的药物", template_id="OUT-E3-OBS-ENTER", target=ST40),
    Branch(priority=4, rule_id="E3-B01..B05", key="routine_action",
           label="常规复评动作", template_id="OUT-E3-*", target="按动作"),
)
```

**约束**

1. 前端通过 `GET /api/domain/branches` 获取该表并**按优先级渲染**（高优先级在上）。
2. 前端必须阻止互斥冲突（如"停用最后一种药"与"仍在使用降糖药"同时为真），并在界面上说明禁用原因。
3. 后端在服务层再次校验优先级，若请求同时命中多个分支，按优先级取第一条，并在响应中返回**被忽略的分支与原因**，禁止静默丢弃。

### 3.3 输出模板冻结

- `domain/templates.py`：30 个 `OUT-*` + 2 个 `SYS-*` 锁定文案（逐字取自实现表）。
- 模板正文为**锁定文字**，改动必须走变更控制。
- 测试 `test_templates_frozen.py` 校验模板 ID 集合与正文哈希；任何改动都会使测试失败，强制回到 spec 流程。
- **计数口径（修正 V1.0-Q-01）**：30 个 `OUT-*` + 2 个 `SYS-*` = 32 条锁定文案。

## 四、数据模型

SQLite（WAL 模式），全部表由 Alembic 管理。

### 4.1 `users`（账号）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | |
| username | TEXT UNIQUE NOT NULL | 登录名 |
| display_name | TEXT NOT NULL | 界面显示姓名（记入事件的操作者） |
| password_hash | TEXT NOT NULL | scrypt 加盐哈希（**禁止明文**） |
| role | TEXT NOT NULL | 本版本仅 `doctor`（预留 `admin`） |
| is_active | INTEGER NOT NULL DEFAULT 1 | 停用标志 |
| created_at / last_login_at | TEXT | ISO8601 |

### 4.2 `patients`（患者档案）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | |
| name / gender / birth_date / medical_record_no | TEXT | 病历号唯一 |
| current_state | TEXT NOT NULL | ST00–ST99 |
| stage / stage_goal / interventions | TEXT | 当前阶段与计划 |
| next_review_date | TEXT | 下次正式复评日期 |
| last_med_stop_date / lifestyle_start_date / surgery_date / earliest_judge_date | TEXT | 观察期时间锚点与系统计算值 |
| remission_confirmed_date | TEXT | 缓解确认日期（形成结论时写入） |
| has_glucose_lowering_drug / drug_purpose | INTEGER / TEXT | F053/F054 的最近确认值 |
| created_at / updated_at | TEXT | |

### 4.3 `events`（临床事件流水，只增不改）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | |
| patient_id | INTEGER FK | |
| operator_id | INTEGER FK → users.id | **操作者**（系统自动事件记系统账号） |
| source | TEXT NOT NULL | `doctor` / `system` |
| rule_id | TEXT NOT NULL | E1-B01 等 |
| source_state / target_state | TEXT NOT NULL | 状态迁移前后 |
| template_id | TEXT | 输出模板 ID（前台不显示） |
| output_text | TEXT NOT NULL | 当时给医生看的自然语言结论 |
| payload | TEXT (JSON) | 当次输入快照（可追溯，含被忽略分支与原因） |
| created_at | TEXT NOT NULL | ISO8601 |

**约束**：事件只增不改；修改历史必须通过新增事件表达。

### 4.4 `audit_log`（系统审计）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id / operator_id / action / target_type / target_id / detail(JSON) / created_at | | |

记录：登录、登出、登录失败、患者建档、事件写入、依据检索、导出、管理操作。

### 4.5 `evidences` / `evidence_chunks`（医学依据检索库）

| 表 | 字段 | 说明 |
| --- | --- | --- |
| evidences | id, title, source_type, file_name, page_count, imported_at | 材料元数据 |
| evidence_chunks | id, evidence_id, page_no, section, content, tokens | 分块正文，用于全文检索 |

检索用 SQLite FTS5（不可用时退化为 `LIKE` 查询 + 关键词高亮）。

### 4.6 `app_meta`

键值表：数据库版本、初始化时间、当前 schema 版本。

## 五、数据库迁移

- 使用 **Alembic**；`alembic upgrade head` 在应用启动时自动执行。
- 首次运行：自动建库 → 执行全部迁移 → 引导创建首个医生账号。
- **禁止**在生产路径使用 `Base.metadata.create_all`。
- 每个迁移脚本必须含中文说明注释，说明本次结构变更原因。

## 六、账号与会话

- 登录：用户名 + 密码；密码 scrypt 加盐哈希；失败计数与短时锁定（基础防护）。
- 会话：签名 Token（含过期时间，默认 8 小时），保存在浏览器本地存储；服务端校验签名与过期。
- **定位声明（V1.0-Q-03）**：账号用于**可追溯性与责任绑定**，本版本面向单机/内网使用，**不承诺**为系统安全边界；正式权限体系（角色矩阵、审计合规、加密存储）不在本版本范围。
- 首次启动无账号时，提供"创建首个医生账号"引导页；不预置默认密码。

---

## 七、时间与提醒

- `core/clock.py` 提供 `Clock` 接口；服务层一律通过 `today` 参数取当天日期（便于测试时间边界）。
- **不做**后台常驻调度（V1.0-Q-04）；到期状态在**登录时与打开工作台时**计算：
  - 观察期：当前日期 ≥ F040 → 提示"已到最早可判定日期，可进入缓解判定"。
  - 正式复评：当前日期 ≥ `next_review_date` → 提示"已到正式复评日期"。
  - 缓解后随访：按第 1 年每 6 个月、第 2 年每 6 个月、满 2 年后每年生成默认提醒。
- 日期计算统一使用 `add_months_clamped`（日历月加法，钳位月末）。

---

## 八、医学依据检索

- 材料导入：把 `_DEV\医学依据` 下的 PDF 抽取为文本 → 分块 → 建索引（脚本 `scripts/import_evidence.py`）。
- 抽取失败（扫描件）时给出明确提示，不做静默降级。
- 检索接口：`GET /api/evidence/search?q=...`，返回命中片段 + 材料名 + 页码。
- 前端入口：页头"医学依据"按钮 → 右侧抽屉（见 `UI.md` 3.8）。
- **措辞纪律**：检索结果只作为**依据查阅**，不得在界面上自动生成临床建议；结果必须显示出处。

## 九、接口约定

| 约定 | 内容 |
| --- | --- |
| 路径 | `/api/...`；流程单元按患者维度组织（`/api/patients/{id}/phase-review` 等） |
| 鉴权 | 除登录与健康检查外，全部接口要求会话 Token |
| 错误 | 业务错误返回 422 + `detail` 为**医生可读的自然语言**；工程异常返回 500 + 通用文案，细节只进日志 |
| 幂等 | 提交类接口接受客户端生成的 `request_id`，重复提交不产生重复事件 |
| 领域导出 | `GET /api/domain/branches`、`GET /api/domain/states` 供前端渲染，保证前后端同源 |
| 审计 | 所有写操作自动写 `audit_log`；审计失败视为整体失败（同事务） |

## 十一、打包路线（便携版）

**目标**：在未安装 Python / Node 的 Windows 机器上双击即用。

```txt
1. frontend: npm run build            → frontend/dist
2. backend : 复制 dist 到 app/static   → FastAPI 静态托管（同源，无 CORS）
3. PyInstaller --onedir               → release/ETMMS/
      ├─ ETMMS启动器.exe               （启动服务 + 打开浏览器 + 托盘退出）
      └─ _internal/                    （Python 运行时、依赖、静态资源）
4. 首次运行：在用户数据目录建库 → 执行迁移 → 引导创建首个医生账号
5. 数据目录：%LOCALAPPDATA%\ETMMS\（含数据库与日志，不写程序目录）
```

**约定**

- 使用 `--onedir`（启动快、易排查），不使用 `--onefile`。
- 打包脚本 `scripts/build.py` 一键完成；产物落 `release/`。
- PyInstaller 与 Python 3.14 的兼容性在 M1 实测；不支持则改用项目内 3.13 虚拟环境（**不改动全局 Python**）。
- 便携版不包含任何真实患者数据；数据库文件不入库、不随包发布。

## 十三、非功能要求

| 维度 | 要求 |
| --- | --- |
| 性能 | 单机使用；任一页面接口响应 < 300ms（万级事件量内） |
| 容量 | 单库支持 ≥ 5 万事件、≥ 5000 患者 |
| 并发 | 单进程单 worker（SQLite 限制）；不承诺多用户并发写入 |
| 日志 | 结构化日志（时间、操作者、动作、结果），滚动保留 90 天 |
| 隐私 | 数据库仅存本机；日志不得记录完整病历内容；导出需审计 |
| 可用性 | 支持离线运行；不依赖任何外部网络服务 |
| 可维护性 | 中文注释齐全；关键路径有测试；新增分支必须同时改 spec、领域表、测试 |

## 十四、关键设计决策汇总

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| AD-01 | 状态转换表与分支优先级集中在 `domain/`，并导出给前端 | 消除"前端一套、后端一套"的漂移，从结构上禁止静默覆盖 |
| AD-02 | 服务层纯函数 + 时间注入 | 可测试日期边界，避免时间相关缺陷 |
| AD-03 | 事件只增不改 + 审计同事务 | 临床决策必须可追溯 |
| AD-04 | Alembic 迁移替代 create_all | schema 演进不丢数据 |
| AD-05 | onedir 便携版，数据写用户目录 | 满足"双击即用"且避免写入受保护目录 |
| AD-06 | 账号定位为可追溯性 | 避免把弱安全机制误当合规方案 |
| AD-07 | 依据检索只提供出处，不给建议 | 系统不得替代医生做医学判断 |
