## 1. 甲方期待我做什么

### 1.1 项目定位

你作为代码学生，需要与临床学生协作，将一份已锁定的临床流程文档转化为**可运行的软件系统**。临床流程不再重新设计——它是既定事实，你需要做的是忠实且严谨地实现它。

### 1.2 软件功能要求（从《临床流程锁定稿》提取）

软件需实现 **5 个医生决策事件 + 1 个系统自动状态**：

| 序号 | 流程单元 | 性质 | 核心功能 |
|------|---------|------|---------|
| 1 | 60秒缓解预评估 | 医生决策事件 | 三类输出：①进入完整评估 ②暂缓（附前置任务+返回位置）③不启动 |
| 2 | 完整评估并形成主动管理计划 | 医生决策事件 | 一次性确认：是否启动、当前阶段（血糖稳定/缓解诱导）、阶段目标、干预组合 |
| 3 | 阶段复评与治疗调整 | 可重复医生决策事件 | 继续/调整/转换阶段/结束主动管理/治疗下血糖达标暂不能判定缓解/停药后自动进入观察期 |
| 4 | 缓解观察期 | **系统自动状态** | 触发条件：停用最后一种降糖药；自动计算最早判定日期；到期提醒 |
| 5 | 缓解判定 | 医生确认事件 | 系统核对5项客观条件后，医生确认"2型糖尿病缓解"结论 |
| 6 | 缓解后复评 | 可重复医生决策事件 | 维持/风险上升/不可评价（器官保护药）/缓解终止→返回主动管理 |

### 1.3 关键临床规则（必须严守的边界）

以下规则**不得在代码中违反**，否则视为验收不通过：

- ❌ 不得使用 ABCD 工具、病程、BMI、HbA1c、胰岛素、C肽作为刚性准入/排除条件
- ❌ 不得设计自动停药、自动减药、或为获得缓解标签而建议停用器官保护药物
- ❌ 不得在多个页面重复收集病程、BMI、分型、C肽、并发症
- ❌ 急性安全/分型存疑/资料缺失不得作为与三类主结论并列的永久状态
- ❌ 不得自增临床节点；状态/标签/自动规则不得伪装为新的临床步骤
- ✅ 前一单元信息自动带入后续，后续只更新变化
- ✅ 关键临床结论必须由医生确认，前台使用自然语言输出
- ✅ 停用最后一种降糖药后系统自动进入缓解观察期（不新增医生确认页面）

### 1.4 需要走通的三个锁定病例

| 病例 | 特征 | 必须避免的错误 |
|------|------|---------------|
| 1 | 43岁女，肥胖 BMI 31，新诊断 T2DM，HbA1c 10.6%，短期胰岛素强化 | 不得因高 HbA1c 或胰岛素排除 |
| 2 | 38岁男，消瘦 BMI 21，早期胰岛素，分型存疑（C肽/抗体未查） | 不得因 BMI 正常/胰岛素/C肽缺失判定不适合；暂缓必须有返回位置 |
| 3 | 52岁女，T2DM 2年，CKD蛋白尿，SGLT2抑制剂，减重10%，HbA1c 5.9% | 不得提示停用器官保护药；正确输出"治疗下血糖达标暂不能判定缓解" |

首轮需联合提交（与临床学生一起）以下4个工作包，且必须互相对齐：

## 2. 技术路线参考与对比

### 2.1 约束条件回顾

| 约束 | 说明 |
|------|------|
| 离线运行 | 软件部署在内网/单机，脱离互联网正常工作 |
| 便于安装 | 不接受脚本版；便携版（文件夹双击即用）或安装程序版（.exe 向导）均可 |
| 前后端分离 | 开发期架构分离，便于维护和协作 |
| 数据持久化 | 需要数据库记录患者评估历史，可追溯 |
| 开发者技能 | Python（主力）、Node.js/JavaScript（辅助）、Windows 环境、VS Code |
| 禁用 Docker | Docker 不方便使用和部署，排除容器化方案 |
| 首轮周期 | 约14天 |

### 2.2 三条技术路线对比

| 维度 | **方案A：FastAPI + React + PyInstaller** ⭐推荐 | 方案B：FastAPI + 静态HTML + PyInstaller | 方案C：Electron + Node.js |
|------|------|------|------|
| **后端框架** | FastAPI (Python) | FastAPI (Python) | Express/Fastify (Node.js) |
| **前端框架** | React (TypeScript) | 纯 HTML/CSS/JS + Alpine.js | React (内嵌于 Electron) |
| **数据库** | SQLite + SQLAlchemy | SQLite + SQLAlchemy | better-sqlite3 |
| **类型安全** | Pydantic (后端) + TypeScript (前端) | Pydantic (后端) | 仅 JS 端弱类型 |
| **打包方式** | PyInstaller → 单文件 .exe | PyInstaller → 单文件 .exe | electron-builder → .exe (≈150MB) |
| **安装体验** | 双击 .exe → 自动打开浏览器 | 双击 .exe → 自动打开浏览器 | 双击 .exe → 独立窗口 |
| **前后端分离** | ✅ 开发期完全分离 | ⚠️ 前端内嵌于后端模板 | ✅ 但打包耦合 |
| **开发效率** | 高：FastAPI 自动生成 OpenAPI 文档，React 生态成熟 | 最高：单文件即可，但交互能力弱 | 中：需处理 Electron 主进程/渲染进程通信 |
| **UI交互能力** | ⭐⭐⭐ 完整 SPA 能力 | ⭐ 有限的页面刷新式交互 | ⭐⭐⭐ 完整 SPA + 原生窗口能力 |
| **可扩展性** | ⭐⭐⭐ 接口清晰，后续可加移动端/云端 | ⭐⭐ 前端逻辑散落，扩展困难 | ⭐⭐ 受限于 Electron 架构 |
| **打包体积** | ≈60-80MB | ≈50-60MB | ≈150-200MB |
| **对 Lifan 友好度** | ⭐⭐⭐ Python 主力，React 学习曲线可控 | ⭐⭐⭐ 几乎纯 Python | ⭐⭐ Node.js 部分能力，Electron 复杂度高 |
| **适用场景** | 需要良好 UI、复杂交互决策流 | 简单表单场景 | 需要原生桌面功能的应用 |

### 2.3 推荐方案详解：A — FastAPI + React + PyInstaller

```
┌─────────────────────────────────────────────────────────┐
│                    用户双击 .exe                         │
└─────────────────────┬───────────────────────────────────┘
                      ▼
┌─────────────────────────────────────────────────────────┐
│               PyInstaller 打包的单文件                    │
│  ┌─────────────────────────────────────────────────┐    │
│  │              Uvicorn + FastAPI                   │    │
│  │  /api/*  →  临床逻辑 API 层                      │    │
│  │  /*      →  静态文件服务 (React build)            │    │
│  └─────────────────────────────────────────────────┘    │
│  ┌─────────────────────────────────────────────────┐    │
│  │  SQLite 数据库 (自动创建于用户数据目录)             │    │
│  └─────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
                      │
                      ▼
             浏览器自动打开 http://localhost:8080
```

**架构分层**：

```
┌─────────────────────────┐
│   React 前端 (SPA)       │  ← 用户交互层
│   状态管理、路由、表单     │
├─────────────────────────┤
│   FastAPI REST API       │  ← 接口层
│   请求校验、路由分发       │
├─────────────────────────┤
│   临床逻辑服务层 (Service) │  ← 核心业务层 ★最严格
│   事件处理、状态转换、规则 │
├─────────────────────────┤
│   数据访问层 (Repository) │  ← 持久化层
│   SQLAlchemy ORM          │
├─────────────────────────┤
│   SQLite                  │  ← 存储层
└─────────────────────────┘
```

**关键优势**：

1. **临床逻辑的可测试性**：核心状态转换逻辑封装在 Python Service 层，可通过 pytest 进行严格的单元测试——这对规则繁多的临床决策流至关重要。
2. **类型安全贯穿全栈**：后端 Pydantic 模型定义输入/输出结构；前端 TypeScript 可与后端共享类型定义（生成 OpenAPI → TypeScript 类型），减少字段不匹配错误。
3. **天然的前后端分离**：开发时前端 `npm run dev` 独立开发，后端 `uvicorn` 独立调试；打包时合为一体。
4. **安装即用**：PyInstaller 将 Python 运行时、依赖库、React 静态文件、SQLite 全部打包为一个 .exe，用户无需安装任何环境。

**需要注意的点**：

- React 需要你投入一定学习成本（JSX、组件化、状态管理）。如果压力较大，可先将前端降级为 HTML + Alpine.js 轻交互方案（表2中的方案B），后续迭代升级。
- PyInstaller 打包时需处理 SQLite 驱动和静态文件路径解析。

## 4. Git 管理与代码结构

### 4.1 Git 分支策略

采用 **简化版 Git Flow**（适合1-2人小项目）：

```
main                 ← 稳定可交付版本（首轮完成时打 tag v0.1.0）
  │
  └── develop        ← 日常开发主线，功能集成于此
        │
        ├── feat/pre-assessment    ← 功能分支：60秒预评估
        ├── feat/full-assessment   ← 功能分支：完整评估
        ├── feat/phase-review      ← 功能分支：阶段复评
        ├── feat/observation       ← 功能分支：缓解观察期
        ├── feat/remission-judge   ← 功能分支：缓解判定
        └── feat/post-remission    ← 功能分支：缓解后复评
```

**规则**：
- `main` 分支只接受来自 `develop` 的合并，合并时打 tag
- `develop` 分支接受来自 `feat/*` 的合并
- 每个 `feat/*` 分支对应一个临床流程单元，完成后合并到 `develop` 并删除
- Bug 修复直接在 `develop` 上处理，紧急修复走 `hotfix/*` → `main` + `develop`

### 4.2 仓库托管

- **主仓库**：GitHub（便于协作、issue 跟踪、代码审查）
- **仓库名建议**：`t2dm-remission-manager`
- **可见性**：Private（涉及临床规则，不宜公开）

## 5. 代码质量保障建议

### 5.1 必须做的（底线）

| 措施 | 工具 | 为什么 |
|------|------|------|
| 类型标注 | Python type hints + Pydantic | 临床字段多且严格，类型错误会导致分支判断出错 |
| 状态机模式 | 自定义 `StateMachine` 类 | 5事件+1自动状态转换必须仅通过合法路径，用状态机模式杜绝非法跳转 |
| 端到端测试 | pytest + 3个锁定病例 | 确保病例1/2/3无错误排除、无错误提示停药、无无出口状态 |
| Git 提交规范 | Conventional Commits | `feat:`, `fix:`, `test:`, `refactor:` 前缀，提交信息清晰 |

### 5.2 强烈推荐的

| 措施 | 工具 | 为什么 |
|------|------|------|
| 代码格式化 | Ruff (Python) + Prettier (前端) | 统一风格，避免格式差异导致的 diff 噪音 |
| 静态检查 | Ruff + mypy (Python); ESLint (前端) | 提交前自动发现类型错误和潜在 bug |
| 单元测试 | pytest-cov | 每个 service 函数都要测，尤其条件分支 |
| 提交前检查 | pre-commit hooks | 自动运行 lint + test，不通过则无法提交 |

### 5.3 临床逻辑的特殊质量要求

这是本项目最关键的环节，普通软件工程方法不够：

```
                    临床流程锁定稿
                          │
                          ▼
              ┌───────────────────────┐
              │  state_machine.py     │  ← 定义合法状态转换矩阵
              │  （唯一的状态转换真源）  │
              └───────────────────────┘
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    service/*.py    api/*.py      frontend/*.tsx
    业务逻辑校验     参数校验       UI展示
          │               │               │
          └───────────────┴───────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  pytest 测试套件       │
              │  覆盖每个分支 + 3病例    │
              └───────────────────────┘
```

**核心原则**：
- `state_machine.py` 是对临床流程锁定稿的可执行翻译，变更它必须同时更新测试和临床流程实现表
- 每个 service 函数必须有明确的输入/输出类型（Pydantic 模型），不接受裸 dict
- 自然语言输出模板集中于一个常量文件，不得硬编码在各处
- "暂缓"状态必须同时返回：原因、前置任务、返回位置——缺少任何一端即为 bug

### 5.4 建议的提交前检查流程

```bash
# 1. 格式化代码
ruff format backend/
prettier --write frontend/

# 2. 静态检查
ruff check backend/
mypy backend/

# 3. 运行测试
pytest backend/tests/ -v --cov=app --cov-report=term

# 4. 如果全部通过，提交
git commit -m "feat: 实现60秒预评估三项主结论分支逻辑"
```
